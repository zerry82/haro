# 시나리오 2. CS까지 떠안은 스타트업 기획자

## 콜드 오픈: 세 개의 알림이 동시에 울린 날

오전 10시 2분, 서연의 화면에는 세 개의 알림이 동시에 떴다.

첫 번째는 고객 메일이었다.

```text
제목: 데이터 업로드 오류가 계속 납니다
```

두 번째는 개발팀 Slack이었다.

```text
이번 주 리포트 기능 우선순위 다시 확인 가능할까요?
```

세 번째는 대표의 메시지였다.

```text
오늘 들어온 고객 이슈, 내일 오전 회의 전에 정리 부탁해요.
```

서연은 세 창을 번갈아 봤다.
고객에게는 지금 답을 해야 했고, 개발팀은 방향을 기다리고 있었고, 대표는 정리된 판단을 원했다.

그런데 정작 서연이 해야 할 일은 신규 리포트 기능 기획서를 쓰는 것이었다.
문서 제목만 열려 있고, 첫 줄은 아직 비어 있었다.

서연은 키보드 위에 손을 올린 채 생각했다.

“내가 기획을 못하는 게 아니라, 기획할 시간을 계속 잃고 있는 거 아닐까.”

## 1. 무너지기 직전의 하루

### 오늘 터진 사건

서연의 명함에는 프로덕트 매니저라고 적혀 있었다. 회사 안에서는 그냥 “기획자”라고 불렸다.

하지만 서연이 실제로 하는 일은 기획이라는 단어로 다 담기지 않았다. 신규 기능 요구사항을 쓰고, 디자인 회의에 들어가고, 개발팀 스프린트를 조율하고, 고객 문의를 확인하고, 버그 재현 영상을 찍고, 공지사항 초안을 쓰고, 대표가 요청한 투자자용 지표도 정리했다.

스타트업에서는 흔한 일이었다. 문제는 그 흔한 일이 더 이상 감당 가능한 양이 아니라는 점이었다.

회사는 B2B SaaS를 만들고 있었다. 고객사는 아직 많지 않았지만, 각 고객사의 요청은 무거웠다.

한 고객사의 관리자 한 명이 막히면 그 회사 전체 도입이 흔들렸다. CS 담당자는 따로 없었다.

초기에는 고객이 적었으니 서연이 직접 답하는 것이 효율적이었다. 하지만 어느 순간부터 고객 문의가 제품 개발보다 더 많은 시간을 먹기 시작했다.

오전 9시 10분, 서연은 Slack을 켜기 전에 Gmail부터 열었다. 읽지 않은 메일이 34개였다.

제목은 비슷했다.

```text
로그인이 안 됩니다
권한 설정 문의
지난번 요청드린 건 확인 부탁드립니다
데이터 업로드 오류
계약 플랜 관련 질문
급합니다
```

문제는 “급합니다”가 항상 진짜 급한 것은 아니라는 점이었다. 어떤 메일은 고객이 단순히 사용법을 모르는 것이었고, 어떤 메일은 실제 장애였다.

어떤 메일은 기능 요청처럼 보였지만 사실은 기존 설정으로 해결 가능했다. 서연은 모든 메일을 열어 본문을 읽고, 고객사 이름을 확인하고, 지난 대화 흐름을 따라가고, 관련 화면을 찾아야 했다.

그 일을 하다 보면 오전이 사라졌다.

10시에는 개발팀 데일리가 있었다. 개발자는 “이번 주 우선순위가 뭐예요?”라고 물었다.

서연은 답을 알고 있어야 했다. 하지만 머릿속에는 고객 문의가 아직 남아 있었다.

권한 설정 문의와 데이터 업로드 오류와 플랜 질문이 뒤섞였다. 서연은 회의 중에도 Gmail 탭을 열어두었다.

고객이 답장을 기다리고 있을 것 같았다.

오후에는 고객사 운영 담당자와 화상 미팅이 있었다. 상대는 정중했지만 피곤해 보였다.

```text
저희 팀에서 같은 질문이 계속 나와요.
권한 설정이 헷갈리고, 업로드 오류가 나면 어디를 봐야 하는지 모르겠어요.
지난번에 메일로 답변 주셨는데, 다시 찾기가 어렵더라고요.
```

서연은 죄송하다고 말했다. 사실 같은 답변을 이미 여러 번 썼다.

권한 설정 안내, 업로드 파일 형식 안내, 관리자 초대 방법, 플랜별 기능 차이. 문제는 답변이 매번 조금씩 달라진다는 점이었다.

고객사의 상황이 다르고, 이전 대화가 다르고, 사용자가 겪는 화면이 달랐다. 복사해서 붙여 넣으면 차갑고 부정확했다.

매번 새로 쓰면 시간이 너무 많이 걸렸다.

저녁 8시, 서연은 제품 기획 문서를 열었다. 오늘 꼭 정리해야 하는 신규 리포트 기능 요구사항이었다.

하지만 이미 하루의 에너지는 고객 문의에 다 쓰였다. 문서 첫 줄을 쓰다가 멈췄다.

그때 Slack 알림이 왔다.

```text
대표: 오늘 들어온 고객 이슈 정리해서 내일 오전까지 공유 가능할까요?
```

서연은 대답했다.

```text
네, 정리해볼게요.
```

그리고 속으로는 생각했다. 무엇을 정리해야 하지?

오늘 온 메일, Slack 문의, 미팅 메모, 개발팀 대화, 고객사별 요청이 모두 흩어져 있었다. 서연은 결국 밤 12시가 넘어서야 “오늘 고객 이슈 정리” 문서를 만들었다.

문서는 나쁘지 않았지만, 내일의 자신을 갈아 넣어 만든 문서였다. 이 방식이 오래갈 수 없다는 것을 서연은 알고 있었다.

그리고 다음 날 아침, 같은 종류의 문의가 다시 들어올 것이라는 것도 알고 있었다.

## 2. haro를 알게 되는 순간

### 고객사가 흘린 힌트

haro를 알게 된 것은 고객사 온보딩 회고 자리였다. 한 고객사의 운영 담당자가 말했다.

```text
저희 내부에서는 문의가 들어오면 먼저 AI가 요청인지 참고인지 나눠주고,
답변 초안까지 만들어주는 도구를 쓰고 있어요.
완전 자동은 아니고 사람이 마지막에 봐요.
```

서연은 처음에는 그 말을 흘려들었다. AI 답변 도구는 이미 많았다.

하지만 상대가 덧붙인 말이 달랐다.

```text
저희가 좋은 건 답변 자체보다, 문의가 업무 흐름으로 남는다는 점이에요.
나중에 이 고객이 왜 이런 요청을 했는지 찾기가 쉬워요.
```

서연은 그 부분에 꽂혔다. 자기에게 필요한 것은 “챗봇”이 아니었다.

고객에게 자동으로 대답하는 것도 아니었다. 필요한 것은 문의가 쌓일 때 그것이 제품 이슈인지, 사용법 질문인지, 정책 문의인지, 버그인지, 기능 요청인지 갈라지는 것이었다.

그리고 답변 초안과 내부 공유 내용이 함께 생기는 것이었다.

그날 밤 서연은 haro를 검색했다. 소개 문구에는 “비개발자를 위한 AI 업무 실행 솔루션”이라고 되어 있었다.

조금 추상적이었다. 하지만 문서 예시 중 Gmail 대화 묶음을 업무 인박스로 다루고, 명확한 요청 메일만 골라낸다는 부분이 눈에 들어왔다.

또 “최종 발송은 사람이 한다”는 문장도 마음에 들었다. 서연은 고객에게 나가는 답변을 자동으로 보내고 싶지는 않았다.

다만 80% 이상 준비된 초안이 있었으면 했다.

다음 날 서연은 대표에게 말했다.

```text
CS 자동응답이 아니라, 문의 정리와 답변 초안부터 해보면 좋겠어요.
저희가 어떤 요청을 많이 받는지도 같이 보이고요.
```

대표는 바로 물었다.

```text
개발 리소스 들어가요?
```

서연은 말했다.

```text
처음에는 Gmail이랑 Drive만 연결해서 써볼 수 있을 것 같아요.
고객에게 자동으로 보내지는 않고, 제가 확인하고 보낼게요.
```

대표는 허락했다. 조건은 하나였다.

고객 데이터가 섞이니 팀 공식 기준과 개인 실험을 구분할 것. 서연은 그 조건이 오히려 마음에 들었다.

흩어진 자료가 아무 데나 섞이는 것은 서연도 싫었다.

실패해도 괜찮았다.
이번 목표는 고객에게 바로 답하는 로봇을 만드는 것이 아니라, 서연의 하루를 삼키는 문의 흐름을 눈에 보이게 만드는 것이었기 때문이다.

## 3. 처음 설정하는 과정

### haro가 처음 던진 질문

haro의 첫 질문은 대행사 사례와 같았다.

```text
어떤 일을 자동화해보고 싶으세요?
```

서연은 이렇게 썼다.

```text
고객 문의 메일과 Slack 문의를 정리하고 싶어요.
사용법 질문, 버그, 기능 요청, 계약 문의를 구분하고,
고객 답변 초안과 내부 공유 메시지를 만들고 싶어요.
```

haro는 곧바로 업무 이해 내용을 보여줬다.

```text
제가 이해한 업무는 이렇습니다.

- 입력: Gmail 문의 대화, Slack 문의, 고객사 정보, 도움말 문서, 기존 답변
- 출력: 고객 답변 초안, 내부 이슈 요약, 기능 요청 후보, 후속 일정
- 과정: 문의 분류 -> 맥락 확인 -> 답변 초안 -> 내부 공유 -> 후속 추적
- 목적: 고객 응대 품질을 유지하면서 기획자가 반복 문의에 소모되는 시간을 줄이는 것
```

서연은 “맞다”고 눌렀다. 그 다음 haro는 Gmail 연결을 제안했다.

다만 전체 메일함을 가져오지 않고, 최근 대화 묶음을 가져와 제목과 본문, 이전 대화 맥락을 읽고 분류한다고 했다. 메일 라벨 설정을 요구하지 않았다.

서연은 Gmail 라벨을 정리해둔 적이 없었기 때문에 이 점이 중요했다. 메일함은 현실적으로 이미 지저분했다.

도구를 쓰기 위해 먼저 메일함을 정리해야 한다면 시작도 못 했을 것이다.

haro는 분류 기준을 설명했다.

- 명확한 요청
- 맥락이 부족한 요청
- 참고 공유
- 시스템 알림
- 뉴스레터
- 민감하거나 개인적인 내용
- 업무 무관

서연은 “명확한 요청만 먼저 보고 싶다”고 했다. haro는 기본 업무 인박스를 그렇게 설정했다.

confidence가 낮은 메일은 자동으로 처리하지 않고 “맥락 부족”으로 보낸다고 했다.

그 다음 haro는 도움말 문서와 기존 답변을 요청했다. 서연은 Google Drive에 있던 FAQ 문서, 온보딩 가이드, 플랜별 기능표, 최근 한 달간 직접 보낸 좋은 답변 몇 개를 가져왔다.

haro는 그것을 팀 공식 기준으로 바로 올리지 않고, 먼저 서연의 작업 공간에 정리했다. 서연이 확인한 뒤 “이건 공식 기준으로 써도 된다”고 승인한 것만 팀 공식 기준 공간으로 올라갔다.

설정 과정에서 서연이 가장 안심한 것은 민감도 질문이었다.

```text
haro: 계약 금액, 장애, 개인정보, 환불 가능성 같은 내용은 민감도가 높은 문의로 볼까요?
```

서연은 그렇다고 했다. 그런 문의는 답변 초안만 만들고, 반드시 사람이 확인하도록 했다.

단순 사용법 질문은 낮은 민감도였다. 하지만 그것도 자동 발송은 하지 않았다.

초안까지만 만들고 사람이 보냈다.

마지막으로 일이 끝난 뒤 이어질 알림과 공유 방식을 정했다. 새로운 명확한 요청이 들어오면 haro 내부 알림은 자동으로 띄운다.

심각도가 높은 버그 후보는 Slack의 `#customer-issues` 채널에 자동 알림을 보낸다. 외부 API 호출이나 고객 메일 발송은 승인 후 또는 초안만 만들도록 했다.

서연은 이 균형이 마음에 들었다. 기계가 고객에게 마음대로 말하지 않지만, 팀이 알아야 할 일은 놓치지 않게 됐다.

그런데 haro는 섞인 일을 억지로 한 덩어리로 처리하지 않았다.
고객에게 답할 일, 개발팀에 넘길 일, 제품 기준을 고칠 일을 조용히 나눠 묻고 있었다.

## 4. 첫 번째 가치 체감

### 문의가 세 갈래로 나뉜 순간

도입 첫날 오후, haro의 업무 인박스에는 열두 개의 Gmail 대화 묶음 중 네 개만 올라왔다. 나머지는 참고 공유, 시스템 알림, 뉴스레터로 접혀 있었다.

서연은 처음에는 의심했다. 혹시 중요한 것을 놓쳤을까 봐 접힌 항목도 열어봤다.

대부분 맞았다.

업무 인박스 첫 번째 대화 묶음은 한 고객사의 권한 설정 문의였다. haro는 이렇게 정리했다.

```text
분류: 명확한 요청
핵심 내용: 고객사 관리자가 신규 멤버 초대 권한을 찾지 못하고 있음
기대 액션: 권한 설정 경로 안내
결과물: 고객 답변 메일
일정: 오늘 중 회신 권장
누락 정보: 고객사가 사용하는 플랜 확인 필요
추천 자료: 관리자 권한 설정 FAQ
```

서연은 플랜 정보를 확인해 입력했다. haro는 답변 초안을 만들었다.

```text
안녕하세요.
문의주신 신규 멤버 초대 권한은 관리자 메뉴의 [팀 관리 > 멤버 초대]에서 확인하실 수 있습니다.
다만 현재 사용 중인 플랜에서는 초대 가능한 관리자 권한이 제한되어 있어,
아래 두 가지 방법 중 하나로 진행하실 수 있습니다.
...
```

초안은 완벽하지 않았지만 구조가 좋았다. 서연은 고객사 이름과 링크를 수정하고 보냈다.

걸린 시간은 4분이었다. 예전에는 같은 답변에 15분은 걸렸다.

FAQ를 찾고, 링크를 확인하고, 표현을 다듬고, 혹시 플랜별 차이가 있는지 다시 봐야 했기 때문이다.

두 번째 대화 묶음은 더 인상적이었다. 고객은 “데이터 업로드가 안 된다”고 썼다.

예전 같으면 서연은 먼저 사과하고, 파일을 보내달라고 하고, 개발팀에 물어봤을 것이다. haro는 이전 대화 흐름을 읽고 이렇게 말했다.

```text
이 문의는 버그일 수도 있지만, 현재 정보만으로는 파일 형식 오류 가능성이 더 높습니다.
고객이 첨부한 파일 이름은 sales_upload_final.xlsx이고,
최근 FAQ 기준으로 필수 컬럼 `customer_id`가 누락되었을 가능성이 있습니다.

추천 액션: 1. 고객에게 필수 컬럼 확인 요청

2. 업로드 템플릿 링크 제공
3. 그래도 실패하면 샘플 파일을 받아 개발팀에 전달

```

서연은 첨부파일을 확인했다. 정말 `customer_id` 컬럼이 없었다.

그 순간 서연은 의자에 기대었다. 이것은 단순 답변 초안보다 컸다.

haro가 고객 문의를 제품 지식과 연결해 원인 후보를 줄여준 것이다. 서연은 고객에게 템플릿 링크와 수정 방법을 보냈고, 개발팀에는 알리지 않았다.

불필요한 내부 이슈가 하나 줄었다.

오후 6시, haro는 오늘의 문의 요약을 만들었다.

```text
오늘 고객 문의 요약

- 권한 설정 문의 3건
- 데이터 업로드 형식 오류 2건
- 실제 버그 의심 1건
- 플랜 문의 1건

반복되는 패턴: - 신규 관리자 온보딩 문서에서 멤버 초대 권한 설명이 부족함

- 업로드 템플릿 위치를 고객이 찾기 어려움
```

서연은 이 요약을 보고 바로 제품 기획 문서에 붙였다. 대표가 요청한 “오늘 고객 이슈 정리”가 10분 만에 끝났다.

그날 서연은 밤 9시에 퇴근했다. 아직 늦은 시간이었지만, 전날의 12시와는 달랐다.

퇴근길에 서연은 처음으로 생각했다. 이걸 잘 쓰면, 내가 다시 기획 일을 할 시간이 생길지도 모르겠다.

## 5. 적응과 확장

### 문의가 팀의 기준으로 바뀐 날

첫 주에는 문의 정리와 답변 초안만 사용했다. 둘째 주부터 서연은 피드백을 주기 시작했다.

```text
이건 버그가 아니라 사용법 질문이에요.
이 고객사는 엔터프라이즈 플랜이라 답변 톤을 더 정중하게 해줘요.
환불 가능성 언급은 제가 확인하기 전에는 쓰지 말아줘요.
```

haro는 이 피드백을 규칙 후보로 저장했다. 서연은 그중 몇 개를 팀 공식 기준으로 승인했다.

- 엔터프라이즈 고객 문의에는 담당 CSM을 참조한다.
- 환불, 계약 해지, 개인정보 관련 문의는 자동 답변하지 않는다.
- 업로드 오류는 먼저 파일 형식과 필수 컬럼을 확인한다.
- 같은 문의가 한 주에 세 번 이상 나오면 도움말 문서 개선 후보로 올린다.

이 규칙들은 서연의 머릿속에 있던 것들이었다. 하지만 머릿속에 있을 때는 매번 피곤했고, 다른 사람에게 넘기기 어려웠다.

haro 안에 규칙으로 남기자 팀원도 같은 기준을 볼 수 있었다.

셋째 주에는 Slack 알림 흐름을 더 적극적으로 썼다. 심각도가 높은 버그 후보가 감지되면 `#customer-issues`에 자동 알림이 갔다.

하지만 고객에게 보내는 답변은 여전히 초안만 만들었다. 서연은 이 선이 중요하다고 느꼈다.

내부 공유는 빠를수록 좋았다. 고객 커뮤니케이션은 마지막 사람이 봐야 했다.

한 번은 haro가 고객 문의를 기능 요청으로 분류했다. 고객은 “관리자 화면에서 사용자별 사용량을 보고 싶다”고 했다.

haro는 답변 초안과 함께 내부 공유 메시지도 만들었다.

```text
기능 요청 후보:
- 고객사: B사
- 요청: 사용자별 사용량 확인
- 배경: 내부 교육 참여율 관리 목적
- 관련 기존 요청: C사, D사에서도 유사 요청 있음
- 추천 처리: 다음 분기 관리자 리포트 기능 discovery에 포함
```

서연은 이 내용을 제품 backlog에 붙였다. 이전에는 고객 문의가 메일함에서 사라지면 기능 요청도 함께 사라졌다.

이제는 요청이 제품 흐름으로 이어졌다. 서연은 이때 haro가 단순 CS 도구가 아니라 제품 팀의 기억 장치가 될 수 있다고 느꼈다.

서연이 놀란 건 처리 속도만이 아니었다.
고객 문의가 제품 기획의 재료로 돌아오기 시작했다는 점이었다.

## 6. 완전 통합

### 다시 제품 기획자로 돌아온 시간

두 달 뒤, haro는 서연 개인 도구에서 팀 운영 방식으로 바뀌었다. 고객 문의가 들어오면 먼저 haro가 대화 흐름으로 묶었다.

명확한 요청만 업무 인박스에 올라왔다. 요청은 사용법 질문, 버그 의심, 기능 요청, 계약 문의, 민감 문의로 나뉘었다.

각 문의에는 핵심 내용, 기대 액션, 필요한 결과물, 일정이 붙었다.

서연은 매일 아침 업무 인박스를 보며 하루 우선순위를 정했다. 개발팀은 `#customer-issues` 채널에서 심각한 버그 후보를 빠르게 확인했다.

대표는 주간 요약에서 어떤 고객 요청이 반복되는지 봤다. 고객 성공 업무를 맡은 신입이 들어왔을 때도, 서연은 긴 인수인계 문서를 새로 만들지 않았다.

haro의 팀 공식 기준 공간을 보여줬다.

```text
여기에 우리가 고객에게 답할 때 지키는 기준이 있어요.
여기는 반복 문의 답변 스킬이고,
여기는 민감 문의 처리 정책이에요.
처음에는 haro가 만든 초안을 보고, 왜 이렇게 답했는지 근거를 같이 보면 돼요.
```

신입은 처음 일주일 동안 haro가 만든 초안을 보며 고객 응대 방식을 익혔다. 서연은 모든 답변을 직접 가르치지 않아도 됐다.

물론 예외는 있었다. 복잡한 계약 문의, 장애 보상, 민감한 고객 불만은 여전히 서연이 직접 봤다.

하지만 반복되는 문의는 더 이상 서연 하루를 삼키지 않았다.

제품 개발에도 변화가 생겼다. 고객 문의 요약이 주간 회의의 고정 안건이 됐다.

“요즘 고객이 뭐라고 하나요?”라는 질문에 서연은 기억을 더듬지 않았다. haro가 분류한 문의 흐름을 보여줬다.

이 주에는 업로드 템플릿 문제가 많았고, 다음 주에는 권한 설정 문의가 줄었고, 특정 기능 요청이 늘었다. 팀은 감으로 일하지 않고 실제 고객 대화에서 반복되는 패턴을 봤다.

## 7. 해피 엔딩

### 서연이 다른 기획자에게 한 말

서연의 일은 여전히 많았다. 스타트업은 늘 새로운 일을 만들었다.

하지만 이제 서연은 하루 종일 문의에 끌려다니지 않았다. 문의는 대화 흐름으로 묶였고, 요청은 분류됐고, 답변 초안은 준비됐고, 내부 공유는 자동으로 이어졌다.

서연은 고객 대응 때문에 제품 기획을 못 하는 날이 줄었다.

가장 큰 변화는 마음의 여유였다. 예전에는 고객 메일이 오면 가슴이 먼저 답답했다.

지금은 haro 업무 인박스를 열고 생각했다. 좋아, 오늘은 어떤 요청이 진짜 중요한지 먼저 보자.

그 차이는 작지 않았다.

한 달 뒤, 서연은 다른 스타트업 PM 모임에서 haro 이야기를 했다. 누군가 물었다.

```text
AI가 고객 답변 보내는 거 불안하지 않아요?
```

서연은 고개를 저었다.

```text
저희는 자동 발송 안 해요.
초안까지만 만들고 사람이 보내요.
근데 진짜 좋은 건 답변이 아니라 분류예요.
메일이 업무로 바뀌고, 반복 문의가 제품 개선으로 이어져요.
그게 제일 커요.
```

그 말은 서연이 직접 겪은 변화였다. haro는 서연을 덜 바쁘게 만든 것만이 아니라, 서연이 다시 제품을 생각할 수 있게 만들었다.

그래서 서연은 haro를 추천할 때 과장하지 않았다. 그냥 이렇게 말했다.

```text
CS 때문에 본업을 못 하고 있으면, 먼저 메일부터 연결해보세요.
전체 자동화 말고, 명확한 요청만 골라보는 것부터요.
거기서 시작하면 꽤 많이 달라져요.
```

## 기능 매핑 박스

| 이야기 속 장면 | haro 기능 |
| --- | --- |
| 고객 문의 thread를 업무 요청으로 묶음 | Gmail CRM형 업무 인박스 |
| label 없이 요청 여부 판단 | Gmail LLM triage |
| 사용법/버그/기능 요청/계약 문의 구분 | workflow router, LLM classification |
| 고객 답변 초안 생성 | Gmail draft, human review |
| 심각한 버그 후보를 Slack에 공유 | messenger_notify hook |
| 반복 문의를 도움말 개선 후보로 저장 | 자연어 규칙 후보, 스킬 제작 |
| 민감 문의는 자동 처리 금지 | hook execution policy, sensitivity policy |
| 신입 온보딩에 팀 기준 활용 | Clean Room |
