# 상세 사용자 시나리오 작성 가이드

## 목적

이 가이드는 haro 시나리오 문서가 기능 나열이나 홍보 문구로 흐르지 않게 하기 위한 기준이다.

각 시나리오는 “제품 설명”이 아니라 “일이 실제로 덜 힘들어지는 과정”을 보여줘야 한다.
독자는 개발자나 제품 담당자가 아닐 수 있다.
문과생, 실무자, 대표, 영업 담당자, 초기 고객이 읽어도 자기 일처럼 이해할 수 있어야 한다.

## 반드시 담을 흐름

### 업무 드라마형 리라이팅 원칙

시나리오는 설명보다 사건으로 시작한다.
독자가 먼저 “이 사람 지금 큰일 났다”라고 느낀 뒤에 배경을 알려준다.

기본 흐름은 아래 순서를 따른다.

```text
사건 -> 감정 -> 작은 해결 -> 다음 사건
```

나쁜 예:

```text
지윤은 메일이 많아서 힘들었다.
haro는 요청 메일을 분류해준다.
```

좋은 예:

```text
전화벨이 울렸다.

“팀장님, 메일 보셨죠?”

지윤은 아직 그 메일을 열어보지도 못했다.
그 순간 Gmail 탭의 읽지 않은 숫자 62가 더 크게 보였다.
```

각 주요 섹션은 5~9개 단락 안에 하나의 작은 장면을 담는다.
장면 안에는 시간, 발화, 파일명, 메일 제목, 엑셀 컬럼, 알림 문구처럼 손에 잡히는 디테일이 있어야 한다.

제품 기능은 먼저 일상 언어의 행동으로 보여준다.
예를 들어 `Gmail LLM triage`라고 설명하지 말고 “오늘 답해야 할 메일 다섯 개만 앞으로 빼줬다”라고 쓴다.
기술 용어는 마지막 `기능 매핑 박스`에만 정리한다.

각 장 끝에는 다음 장면이 궁금해지는 작은 걸림돌을 남긴다.

```text
그런데 문제는 다음 날 다시 터졌다.
은정이 놀란 건 답변 속도가 아니었다.
처음으로 지윤은 다른 선택을 해봤다.
```

### 1. 무너지기 직전의 하루

업무의 양과 정서적 압박을 먼저 보여준다.

나쁜 예:

```text
사용자는 업무가 많다.
```

좋은 예:

```text
오전 9시 20분, 메일함에는 이미 읽지 않은 메일이 47개였다.
그중 무엇이 고객 요청이고, 무엇이 단순 참조인지 구분하는 데만 30분이 사라졌다.
```

### 2. haro를 알게 되는 순간

광고처럼 보이면 안 된다.
지인 추천, 팀 내부 실험, 검색, 대표의 제안, 커뮤니티 글처럼 자연스러운 접점을 둔다.

### 3. 친근한 설정 과정

haro는 어려운 설정 화면으로 시작하지 않는다.
“어떤 일을 자동화하고 싶으세요?” 같은 질문에서 시작한다.

Gmail, Google Drive, Excel, Slack 같은 연결은 기술 설정이 아니라 업무 문장으로 설명한다.

```text
haro: 고객 요청 메일이 주로 들어오는 Gmail 계정을 연결할까요?
haro: 매체 리포트가 모이는 Drive 폴더가 있나요?
haro: 완료되면 팀 Slack에 알릴까요?
```

### 4. 첫 번째 가치 체감

사용자가 처음으로 “아, 이거 진짜 내 일을 이해한다”라고 느끼는 장면이 있어야 한다.
이 장면은 작아도 좋다.
메일 하나를 정확히 골라주거나, 엑셀 컬럼 하나를 기억하거나, 매번 놓치던 후속 일정을 알려주는 순간이면 된다.

### 5. 적응과 확장

haro는 처음부터 완벽하지 않다.
사용자가 피드백을 준다.
haro가 그것을 규칙 후보로 저장한다.
검증된 규칙이 스킬이 된다.
팀이 쓰는 공식 기준은 Clean Room으로 올라간다.

### 6. 완전 통합

haro가 개인 보조 도구를 넘어 팀의 일하는 방식이 되는 장면을 보여준다.
누가 쉬어도 업무 기준이 남아 있고, 신규 구성원이 들어와도 따라갈 수 있어야 한다.

### 7. 해피 엔딩

단순히 “행복해졌다”가 아니다.
다음 변화가 구체적으로 보여야 한다.

- 야근이 줄었다.
- 실수가 줄었다.
- 고객 응대가 빨라졌다.
- 담당자가 자신감을 회복했다.
- 팀이 같은 기준으로 일하게 됐다.
- 사용자가 haro를 누군가에게 자연스럽게 추천한다.

## 어려운 용어 번역 규칙

| 제품 용어 | 시나리오 본문 표현 |
| --- | --- |
| Gmail LLM triage | 요청 메일만 골라주는 기능 |
| Google Drive import | Drive에서 필요한 파일만 가져오기 |
| Playground | 내 실험 공간 |
| Clean Room | 팀 공식 기준 공간 |
| Skill | 다음에도 반복할 수 있게 저장된 업무 방식 |
| Hook | 일이 끝나면 알림, 저장, 초안을 이어서 해주는 장치 |
| Project Fork | 잘된 프로젝트의 일하는 방식을 다른 프로젝트에 복사하는 기능 |
| Human Review | 사람이 마지막으로 확인하는 단계 |

기술 용어는 본문에 남발하지 않는다.
필요하면 마지막 `기능 매핑 박스`에서만 정리한다.

## 금지 사항

- haro가 모든 문제를 한 번에 완벽히 해결한다고 쓰지 않는다.
- 사용자가 아무 판단도 하지 않는 것처럼 쓰지 않는다.
- 자동 메일 발송을 기본값처럼 쓰지 않는다.
- 고객 데이터와 개인 정보를 가볍게 다루지 않는다.
- 실무자의 고통을 희화화하지 않는다.
- 과장된 감탄사나 광고 카피로 결말을 밀어붙이지 않는다.

## 권장 문장 감각

좋은 시나리오는 조용하지만 설득력이 있어야 한다.
사용자가 팬이 되는 이유는 거창한 혁신 때문이 아니라, 매일 반복되던 부담이 조금씩 사라지는 경험 때문이다.

```text
그날 지윤은 처음으로 보고서 숫자를 두 번 확인하는 데 시간을 쓰지 않았다.
대신 광고주에게 보낼 다음 주 액션을 생각했다.
그게 원래 자기 일이었다는 사실을, 오랜만에 다시 떠올렸다.
```
