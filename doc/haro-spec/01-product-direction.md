# haro 제품 방향

## 1. 문제 정의

haro의 사용자는 개발자가 아니다.
기획, 마케팅, HR, 재무, 법무, 영업, CS, 운영, 리서치처럼 파일과 보고서와 커뮤니케이션을 매일 다루지만 코드를 직접 작성하지 않는 화이트칼라 팀원이다.

이들이 겪는 문제는 “AI에게 질문하기 어렵다”가 아니라 “일이 파일과 규칙과 맥락과 의사결정으로 흩어져 있다”는 것이다.

화이트칼라 업무에서 반복되는 문제는 다음과 같다.

- 입력 파일과 자료 형식이 제각각이다.
- 팀, 고객, 프로젝트마다 판단 기준과 선호가 다르다.
- 업무규칙과 예외 처리가 사람 머릿속에 남는다.
- 사용자와 커뮤니케이션 대상의 선호, 주의점, 관계 히스토리가 숨은 맥락으로 남는다.
- 담당자가 바뀌면 기준과 히스토리가 끊긴다.
- 산출물은 보고서, 대시보드, 제안서, 검토 의견, 공유 링크처럼 매번 다른 형태로 필요하다.
- 결정적 계산과 비결정적 판단이 한 업무 안에 섞여 있다.

대행사/마케팅 업무는 haro를 적용할 수 있는 대표 예시 중 하나다.
haro의 대상은 특정 직종이 아니라, 반복 가능한 판단 흐름을 가진 화이트칼라 업무 전반이다.

## 2. 제품 정의

haro는 비개발자가 자기 업무 파일, 업무규칙, 의사결정 기준을 맡기면 이를 정리하고 기억하고 반복 실행 가능한 workflow로 바꿔주는 AI 업무 실행 솔루션이다.

한 문장으로는 다음과 같다.

```text
haro는 흩어진 업무 파일, 규칙, 결정, 산출물, 이벤트를 작업 하네스로 묶고,
사용자의 자연어 업무규칙을 검증 가능한 workflow 스킬로 바꾸는 AI 코워크 솔루션이다.
```

haro의 기본 믿음은 다음이다.

```text
화이트칼라 업무는 workflow다.
결정적 계산이든 비결정적 판단이든,
입력, 조건, 결정, 산출물, 검증 기준이 있으면 자동화 가능하다.
```

여기서 workflow는 단순 순서도가 아니다.
자료 확인, 조건 분기, 사람 승인, LLM 판단, 코드 실행, 외부 이벤트 대기, 산출물 검증이 연결된 의사결정 트리다.

haro의 확장 방식은 직종별 hard-coded 제품을 만드는 것이 아니다.
성공한 프로젝트의 workflow meta를 템플릿화하고, 이를 새 프로젝트와 다른 vertical에 복제/변형하는 방식이다.

예를 들어 대행사에서 광고주 1개 프로젝트에 haro 도입이 성공하면, 실제 광고주 데이터와 개인 작업공간은 제외하고 Meta Clean Room 설정만 template으로 저장한다.
이 template을 나머지 광고주 프로젝트 생성 시 적용해 같은 자동화 구조를 빠르게 확산한다.

haro는 전체 팀원이 함께 쓰는 공간이다.
따라서 팀 기준을 보호하는 `Clean Room`과 사용자별 자유 실험 공간인 `User Playground`를 구분한다.
Clean Room은 다시 공식 업무 데이터의 `Data Clean Room`과 공식 규칙/스킬의 `Meta Clean Room`으로 나눈다.

haro는 파일과 규칙만 기억하지 않는다.
메일, 채팅, 피드백에서 반복 관찰되는 사람 맥락도 숨은 맥락으로 관리한다.
여기서 인간분석은 성격 단정이 아니라, 사용자의 업무 선호와 주요 커뮤니케이션 대상의 관찰 가능한 업무 패턴을 답장 초안과 우선순위 판단에 보조로 쓰는 것이다.

## 3. 두 가지 핵심 포인트

### 3.1 강력한 하네스

하네스는 AI가 안전하고 정확하게 일하기 위한 작업틀이다.

현재 구현된 파일 트리, 업로드, CSV 편집, HTML/Markdown 미리보기는 하네스의 기초다. 다음 단계의 하네스는 파일을 단순히 보여주는 데서 끝나면 안 된다.

하네스는 다음을 해야 한다.

- 파일을 업무 목적별로 정리한다.
- Google Drive 같은 외부 데이터소스를 내부 파일시스템과 명확히 분리해 가져온다.
- 팀 공식 기준과 개인 실험 공간을 분리한다.
- 공식 데이터와 공식 메타 규칙을 분리해 보호한다.
- workflow의 입력, 결정, 산출물, 검증 기준을 추적한다.
- 채팅세션을 작업 폴더와 기록 파일로 정리한다.
- 업로드된 파일의 성격을 파악한다.
- 파일별 처리 상태를 보여준다.
- 산출물과 원본 데이터를 연결한다.
- 대화에서 나온 결정과 규칙 후보를 파일로 남긴다.
- 사용자가 “이 파일은 뭐였지?”를 묻지 않게 한다.
- AI가 어떤 파일을 근거로 작업했는지 추적 가능하게 한다.
- 사용자와 주요 커뮤니케이션 대상의 숨은 사람 맥락을 필요할 때만 참고한다.

### 3.2 비개발언어로 스킬 제작

스킬은 코드 플러그인이 아니라 workflow의 실행 단위다.
스킬은 사용자의 자연어 업무 설명을 입력, 프로세스, 결정, 산출물, 검증 기준으로 구조화한 것이다.

사용자는 다음처럼 말해야 한다.

```text
계약서 검토할 때 책임 제한 조항이 없으면 먼저 표시해줘.
금액이 1천만 원 넘으면 팀장 승인 단계도 넣어줘.
최종 결과는 검토 의견서와 수정 요청 목록으로 만들어줘.
```

haro는 이를 다음처럼 구조화해야 한다.

- 적용 대상: 계약서 검토 workflow
- 규칙 유형: 데이터 규칙, 판단 규칙, 승인 규칙, 산출물 규칙
- 실행 시점: 계약서 파일 업로드 또는 “검토해줘” 명령
- 검증 방법: 사용자가 결과를 확인하고 승인
- 저장 형태: 다음 작업에서 재사용 가능한 스킬

## 4. 현재 구현과 다음 제품의 차이

| 영역 | 현재 구현 | 다음 목표 |
| --- | --- | --- |
| 파일 | 트리 탐색, 업로드, 편집 | Data/Meta Clean Room과 User Playground 분리, 업무 단위 정리, 상태 추적, 파일 의미 분류 |
| 채팅 | DB 기반 채팅 목록과 메시지 | 채팅세션을 작업 폴더로 관리하고 결정/규칙/산출물 파일화 |
| CSV/Excel | Excel 업로드 시 CSV 변환, 셀 편집 | 직무별 데이터 타입 인식, 정규화 제안 |
| 데이터소스 | 빈 데이터소스 탭 | Google Drive 같은 외부 원천을 연결하고 선택 파일을 Playground로 가져오기 |
| 사람 맥락 | 없음 | 사용자와 주요 커뮤니케이션 대상의 업무 선호를 숨은 맥락으로 관리하고 초안/우선순위에 반영 |
| 스킬 | 스킬 목록 표시 | 업무 이해, decision workflow 설계, 샌드박스 검증, trigger/hook 설정, 활성화 |
| 에이전트 | 도구 호출 기반 파일 작업 | 하네스 상태와 스킬을 근거로 반복 업무 수행 |
| 산출물 | HTML/Markdown/CSV/코드 미리보기 | 보고서, 대시보드, 제안서, 검토 의견, 공유 패키지 관리 |

## 5. 제품 원칙

1. 사용자는 폴더 구조를 외우면 안 된다.
2. haro가 먼저 업무 폴더를 제안해야 한다.
3. 스킬은 코드가 아니라 업무 문장으로 시작해야 한다.
4. 모든 자동화는 원본 파일, 결정 근거, 적용 규칙을 추적할 수 있어야 한다.
5. Clean Room의 팀 기준은 승인 없이 깨지면 안 된다.
6. 공식 데이터와 공식 규칙/스킬은 서로 다른 변경 이력으로 보호해야 한다.
7. Playground는 사용자별로 제공되어 마음껏 실험할 수 있어야 한다.
8. 비개발자는 실패했을 때 코드를 고치는 대신 “무엇이 틀렸는지”만 말할 수 있어야 한다.
9. 기억은 많을수록 좋은 것이 아니라, 적용 범위와 최신성이 명확해야 한다.
10. 대행사 시나리오는 대표 vertical example이며, 제품 구조는 화이트칼라 업무 전반에 열려 있어야 한다.
11. 성공한 workflow meta는 프로젝트 fork를 통해 template family로 확장 가능해야 한다.
12. 외부 데이터소스는 공식 저장소가 아니라 원천 연결이며, haro로 가져온 snapshot만 하네스 정책을 따른다.
13. 사람 맥락은 성격 단정이나 심리 진단이 아니라 관찰 가능한 업무 선호로만 다룬다.
14. 사람 맥락은 Project Fork와 Clean Room Git에 포함하지 않고, 요약 노출과 수정/삭제를 지원해야 한다.
