# 기술 POC 핵심 개념

이 문서가 기술 POC의 기준 문서다.

다른 기술 문서와 구현 계획은 이 문서의 개념을 더 구체화한 하위 문서로 본다.

## 1. 왜 다시 정리하는가

초기 POC 문서는 마케팅 업무 예시를 중심으로 작성되어 있다. 예를 들어 `CSV 업로드`, `리포트 생성`, `이메일 초안 작성` 같은 표현이 많다.

하지만 기술 POC에서 먼저 검증해야 하는 것은 특정 마케팅 업무가 아니라 더 본질적인 실행 능력이다.

이번 POC의 목적은 수요검증이 아니다. 고객이 이 제품을 원하는지 확인하는 단계가 아니라, 우리가 상상한 실행환경이 기술적으로 가능한지 확인하는 단계다.

따라서 질문은 “누가 살 것인가?”가 아니라 다음이다.

> 프로젝트별 샌드박스 안에서 파일, 코드, 브라우저, 웹서버, 아카이브를 하나의 실행 루프로 묶을 수 있는가?

이 샌드박스는 POC와 초기 제품에서 Docker 기반으로 구현한다. VM/microVM은 현재 결정이 아니라, 보안/운영 요구가 커졌을 때 검토할 미래 옵션이다.

예를 들어:

| 구체 예시 | 본질 개념 |
| --- | --- |
| CSV 업로드 | 파일 업로드 |
| 엑셀 정리 | 파일 읽기/쓰기와 코드 실행 |
| 리포트 생성 | 산출물 생성 |
| 대시보드 호스팅 | 웹서버 실행과 엔드포인트 노출 |
| 이메일 초안 | 텍스트 산출물 생성 |
| 캠페인 자동화 | 트리거 기반 작업 실행 |
| 웹사이트 로그인/조회 | 브라우저 관찰과 DOM 기반 실행 |
| 2FA 입력 | 사용자 개입 지점 |

따라서 POC는 마케팅 도메인 전체에 묶기보다, 먼저 **Docker 기반 project sandbox가 에이전트 실행환경으로 충분한가**를 검증해야 한다.

## 2. 핵심 개념

기술 POC의 핵심은 다음 7개 개념으로 압축할 수 있다.

1. 프로젝트
2. 샌드박스
3. 파일
4. 코드 실행
5. 서비스 노출
6. 브라우저 실행
7. 상태 보존

이 7개가 작동하면, 그 위에 마케팅 업무, 스킬, 페르소나, 자동화를 올릴 수 있다.

## 3. 프로젝트

프로젝트는 하나의 업무 단위다.

마케팅에서는 캠페인, 브랜드, 고객사, 월간 운영 단위가 프로젝트가 될 수 있다. 하지만 기술적으로는 다음을 묶는 최상위 단위다.

- 샌드박스
- 파일
- 실행 로그
- 사용자 권한
- 스킬
- 페르소나
- 트리거
- 배포된 결과물

본질적으로 프로젝트는 **공유 가능한 작업 컨텍스트**다.

## 4. 샌드박스

샌드박스는 프로젝트를 실행하는 격리된 컴퓨팅 환경이다.

여기서 중요한 것은 “마케팅용 환경”이 아니라 다음 능력이다.

- 격리된 파일시스템
- 격리된 프로세스
- 제한된 리소스
- 코드 실행 가능성
- 네트워크/포트 제어
- 종료와 재시작 가능성

본질적으로 샌드박스는 **프로젝트별 임시 컴퓨터**다.

## 5. 파일

파일은 샌드박스 안에서 에이전트와 사람이 함께 다루는 가장 기본적인 작업 대상이다.

CSV, XLSX, PDF, 이미지, Markdown, JSON, 코드 파일은 모두 구체 타입일 뿐이다.

기술 POC에서 확인할 것은 다음이다.

- 파일을 넣을 수 있는가?
- 파일을 읽을 수 있는가?
- 파일을 수정할 수 있는가?
- 새 파일을 만들 수 있는가?
- 파일을 삭제하거나 이동할 수 있는가?
- 파일 변경 이력을 추적할 수 있는가?

본질적으로 CSV 업로드는 **파일 업로드**다.

본질적으로 엑셀 정리는 **파일 읽기, 코드 실행, 파일 쓰기**다.

## 6. 코드 실행

코드 실행은 에이전트가 단순히 답변만 하는 존재가 아니라 실제 작업을 수행하는 존재가 되기 위한 핵심이다.

기술 POC에서 확인할 것은 다음이다.

- 코드를 생성할 수 있는가?
- 코드를 저장할 수 있는가?
- 코드를 실행할 수 있는가?
- 실행 중 파일을 읽고 쓸 수 있는가?
- 실행 결과와 에러를 기록할 수 있는가?
- 실패한 코드를 수정하고 재실행할 수 있는가?

본질적으로 데이터 정리, 리포트 생성, 대시보드 생성은 모두 **코드 실행 기반 산출물 생성**이다.

## 7. 서비스 노출

서비스 노출은 샌드박스 안에서 만든 결과물을 외부 사용자가 접근할 수 있게 하는 능력이다.

구체적으로는 다음 예시가 있다.

- 웹 페이지 미리보기
- 정적 리포트 공유
- 대시보드 접속
- API 엔드포인트 제공
- 임시 앱 실행

하지만 본질은 하나다.

> 샌드박스 안의 프로세스 또는 파일을 외부 URL로 연결할 수 있는가?

이 능력이 있으면 단순한 파일 생성 도구를 넘어, 실제 업무 결과물을 서비스처럼 보여줄 수 있다.

마케터 입장에서는 이것이 “광고주나 의사결정자에게 보낼 예쁜 대시보드 링크”가 된다.

## 8. 브라우저 실행

브라우저 실행은 에이전트가 웹 서비스를 사람처럼 다루기 위한 능력이다.

마케팅 업무에서는 광고 관리자, CRM, 이메일, 분석 대시보드, 협업툴 같은 외부 웹서비스를 다뤄야 한다. 이때 단순 HTTP 호출이나 스크래핑만으로는 부족하다.

기술 POC에서 확인할 것은 다음이다.

- 샌드박스 안에서 Chromium을 실행할 수 있는가?
- Playwright로 페이지 이동, 클릭, 입력을 수행할 수 있는가?
- 현재 화면을 screenshot으로 저장할 수 있는가?
- 현재 화면의 accessibility snapshot과 visible DOM을 추출할 수 있는가?
- DOM element의 bounding box를 계산할 수 있는가?
- screenshot 위에 element id overlay를 그릴 수 있는가?
- LLM은 overlay screenshot을 보고 판단하고, 실행은 DOM/ref 기반으로 할 수 있는가?
- 2FA/MFA가 필요한 순간에 사용자가 브라우저 화면에 개입할 수 있는가?

본질적으로 웹사이트 로그인/조회는 **브라우저 관찰과 DOM 기반 실행**이다.

브라우저 도구의 기본 원칙은 다음이다.

```text
해석: visual overlay
실행: DOM/accessibility ref
```

순수 screenshot 기반 실행은 좌표 오차가 생기기 쉽다. 순수 DOM 기반 실행은 LLM이 실제 화면 배치를 이해하기 어렵다. 따라서 둘을 결합한다.

```text
BrowserTool.observe()
  -> screenshot
  -> accessibility snapshot
  -> visible DOM elements
  -> bounding boxes
  -> overlay screenshot
  -> element_id map

BrowserTool.action()
  -> element_id
  -> Playwright locator/ref
  -> click/type/select
```

2FA/MFA는 자동화 대상이 아니라 사용자 개입 지점으로 본다.

```text
Agent detects 2FA
  -> user takeover
  -> user completes verification
  -> agent resumes
```

## 9. 상태 보존

샌드박스는 계속 켜두면 비용이 든다. 따라서 비활성화와 재활성화가 가능해야 한다.

기술 POC에서 확인할 것은 다음이다.

- 현재 파일 상태를 저장할 수 있는가?
- 실행 로그를 저장할 수 있는가?
- 설정과 메타데이터를 저장할 수 있는가?
- 실행 중인 프로세스를 안전하게 종료할 수 있는가?
- 나중에 다시 활성화했을 때 이전 상태를 복구할 수 있는가?
- 사용자별 browser profile을 보존하고 복구할 수 있는가?

본질적으로 이것은 **작업공간의 저장과 복구**다.

## 10. 스킬, 페르소나, 트리거의 본질

초기 문서에는 `skills/`, `personas/`, `triggers/`가 별도 영역으로 정의되어 있다.

이들도 더 본질적인 개념으로 환원할 수 있다.

| 개념 | 본질 |
| --- | --- |
| 스킬 | 반복 가능한 작업 절차 |
| 페르소나 | 역할 기반 응답 정책 |
| 트리거 | 특정 조건에서 작업을 시작하는 규칙 |

즉:

- 스킬은 “어떻게 처리할지”에 대한 로직이다.
- 페르소나는 “어떤 관점/역할로 말할지”에 대한 정책이다.
- 트리거는 “언제 실행할지”에 대한 조건이다.

기술 POC에서는 이것들을 완성된 기능으로 만들 필요는 없다. 먼저 파일 또는 설정으로 존재할 수 있고, 샌드박스 안에서 읽고 실행될 수 있으면 된다.

## 11. 가장 단순한 POC 루프

마케팅 도메인을 걷어내면 가장 단순한 POC 루프는 다음이다.

```text
프로젝트 생성
  -> 샌드박스 생성
  -> 파일 업로드
  -> 코드 생성
  -> 코드 실행
  -> 새 파일 생성
  -> 브라우저 실행
  -> 화면 관찰
  -> DOM 기반 액션 수행
  -> 웹으로 결과 확인
  -> 샌드박스 비활성화
  -> 상태 저장
  -> 샌드박스 재활성화
  -> 이전 상태 확인
```

이 루프가 되면 마케팅 업무는 그 위에 올릴 수 있다.

## 12. LLM 적용 전의 본질 검증

LLM 없이 먼저 검증해야 할 것은 다음이다.

| 질문 | 의미 |
| --- | --- |
| 사람이 파일을 넣을 수 있는가? | 파일 관리 가능성 |
| 사람이 코드를 만들고 실행할 수 있는가? | 실행환경 가능성 |
| 코드가 다른 파일을 읽고 쓸 수 있는가? | 작업 수행 가능성 |
| 브라우저를 실행하고 화면을 관찰할 수 있는가? | 웹 작업 가능성 |
| overlay 화면의 element를 DOM 기반으로 실행할 수 있는가? | 안정적인 브라우저 조작 |
| 결과를 URL로 볼 수 있는가? | 서비스 노출 가능성 |
| 껐다 켜도 남아 있는가? | 상태 보존 가능성 |

이 단계가 되지 않으면 LLM을 붙여도 제품이 되지 않는다.

## 13. LLM 적용 후의 본질 검증

LLM을 붙인 뒤 확인할 것은 다음이다.

| 질문 | 의미 |
| --- | --- |
| LLM이 파일 구조를 이해하는가? | 작업공간 이해 |
| LLM이 적절한 파일을 읽는가? | 컨텍스트 선택 |
| LLM이 필요한 코드를 만드는가? | 작업 계획과 구현 |
| LLM이 코드를 실행하고 실패를 고치는가? | 반복 수행 |
| LLM이 overlay screenshot을 해석하는가? | 시각적 화면 이해 |
| LLM이 element id를 선택하고 DOM 기반 action을 수행하는가? | 안정적 브라우저 실행 |
| LLM이 산출물을 올바른 위치에 저장하는가? | 결과 관리 |
| LLM이 결과를 설명하는가? | 사용자 협업 |

LLM은 본질 기능 위에 올라가는 작업자다. 따라서 먼저 본질 기능이 있어야 한다.

## 14. 한 문장 정의

기술 POC의 한 문장 정의:

> 프로젝트별 격리 샌드박스에서 파일을 다루고, 코드를 실행하고, 브라우저를 조작하고, 결과를 웹으로 노출하며, 상태를 저장/복구할 수 있는 최소 실행환경을 만든다.

이것이 되면 다음 단계에서 LLM이 그 환경을 사용하도록 만들 수 있다.

## 15. POC 범위 재정의

이번 POC에서 반드시 필요한 것:

- 프로젝트 생성
- 샌드박스 생성
- 파일 업로드/조회/수정
- 코드 저장/실행
- 실행 결과 파일 생성
- 보고서/대시보드 생성
- 브라우저 실행
- overlay screenshot 생성
- DOM 기반 브라우저 액션
- 2FA/MFA 사용자 개입
- 웹서버 또는 정적 결과물 노출
- 샌드박스 비활성화
- 상태 아카이빙
- 샌드박스 재활성화

이번 POC에서 아직 본질이 아닌 것:

- 수요검증
- 고객 인터뷰
- 가격/과금
- 제품 포지셔닝
- 완성형 마케팅 자동화
- 완성형 이메일 에이전트
- 고도화된 권한 관리
- 복잡한 워크플로우 빌더
- 완전한 멀티테넌시
- 고급 대시보드
- 대규모 동시 실행
- 범용 원격 데스크톱
- 고도화된 anti-bot 회피
- VM/microVM 도입

먼저 작은 실행환경을 증명한다. 그 다음에 마케팅 도메인을 입힌다.

## 16. POC 성공 후 최소 인프라 구성

POC가 성공했다는 것은 다음 최소 기술 루프가 가능하다는 뜻이다.

```text
프로젝트 생성
  -> Docker sandbox 생성
  -> 파일 조작
  -> 코드 실행
  -> 브라우저 조작
  -> 보고서/대시보드 생성
  -> 웹 링크 노출
  -> 아카이브
  -> 복구
```

이 루프가 검증되면, 초기 서비스에 필요한 최소 인프라는 다음과 같다.

```text
User Browser
  -> Web App
  -> Control Plane API
  -> Docker Host
       -> Project Sandbox Containers
       -> Workspace Volumes
       -> Playwright/Chromium
       -> Report/Dashboard Preview Servers
  -> Reverse Proxy
  -> PostgreSQL
  -> Object Storage
```

### 16.1 최소 구성

초기에는 단일 VM 또는 단일 서버에서 시작할 수 있다.

```text
single cloud VM
  -> web app
  -> api server
  -> docker engine
  -> traefik
  -> postgres
  -> minio
```

각 컴포넌트의 역할은 다음과 같다.

| 구성요소 | 역할 |
| --- | --- |
| Web App | 사용자가 프로젝트, 자료, 실행 상태, 결과물을 보는 UI |
| Control Plane API | 프로젝트 생성, 파일 조작, 실행 요청, 브라우저 요청, 아카이브 요청 처리 |
| Docker Engine | 프로젝트별 sandbox container 실행 |
| Traefik | sandbox 내부 preview/report 서버를 외부 URL로 연결 |
| PostgreSQL | 프로젝트, 실행 로그, 파일 메타데이터, 아카이브 메타데이터 저장 |
| MinIO/S3/R2 | workspace archive, 생성 산출물, 첨부파일 저장 |
| Docker Volume | 활성 프로젝트 workspace 저장 |

### 16.2 최소 배포 형태

첫 배포는 다음 정도면 충분하다.

```text
cloud VM 1대
  docker compose
    web
    api
    traefik
    postgres
    minio
    sandbox-runtime-image
```

이 구조의 목적은 대규모 운영이 아니다. POC에서 확인한 루프를 실제 서버에서 반복 가능하게 만드는 것이다.

### 16.3 프로젝트 활성화 흐름

```text
프로젝트 생성
  -> DB에 project 생성
  -> Docker volume 생성
  -> workspace 기본 구조 생성
  -> sandbox container 시작
  -> project 상태 active
```

### 16.4 프로젝트 비활성화 흐름

```text
프로젝트 비활성화
  -> 실행 중 프로세스 정리
  -> workspace tar.gz 생성
  -> object storage 업로드
  -> sandbox container 정리
  -> 필요 시 volume 삭제
  -> project 상태 archived
```

### 16.5 프로젝트 재활성화 흐름

```text
프로젝트 재활성화
  -> object storage에서 archive 다운로드
  -> Docker volume 생성
  -> workspace 복구
  -> sandbox container 시작
  -> project 상태 active
```

### 16.6 최소 URL 구조

사용자가 보는 URL은 단순해야 한다.

```text
https://app.example.com/projects/{project_id}
https://app.example.com/projects/{project_id}/files
https://app.example.com/projects/{project_id}/runs
https://app.example.com/projects/{project_id}/report
https://preview.example.com/p/{project_id}
```

광고주나 의사결정자에게 공유하는 URL은 다음처럼 별도로 둔다.

```text
https://share.example.com/r/{report_id}
```

### 16.7 최소 확장 기준

단일 서버에서 다음 문제가 생기면 그때 분리한다.

| 문제가 생기는 지점 | 다음 확장 |
| --- | --- |
| sandbox 실행이 web/api를 방해함 | sandbox 전용 worker 서버 분리 |
| PostgreSQL 부하/백업 필요 | managed PostgreSQL로 이전 |
| archive 용량 증가 | S3/R2로 이전 |
| preview 트래픽 증가 | reverse proxy와 sandbox host 분리 |
| 고객별 보안 요구 증가 | 고객별 Docker host 또는 VM/microVM 검토 |
| 동시 실행 증가 | sandbox worker pool 구성 |

### 16.8 이 단계에서 여전히 하지 않는 것

POC 성공 직후의 최소 인프라에서도 아직 하지 않는다.

- Kubernetes 도입
- VM/microVM 도입
- 고객별 전용 인프라
- 복잡한 멀티테넌시
- 대규모 auto-scaling
- 고급 billing/resource quota
- 완성형 workflow builder

먼저 단일 Docker host에서 반복 가능한 실행 루프를 안정화한다.
