# Claude-Style Plan Mode Spec

작성일: 2026-05-09

## 문제

현재 하로의 복잡한 작업 흐름은 사용자 요청, 요구사항 해석, 계획, 도구 실행, 최종 보고가 한 번의 intent turn 안에서 섞이기 쉽다. 이 구조에서는 다음 문제가 반복될 수 있다.

- 요구사항이 확정되기 전에 파일 생성이나 수정이 시작된다.
- 계획 문서와 실행 TODO가 구분되지 않아 사용자가 중간에 방향을 바꾸기 어렵다.
- "스펙을 만들자" 같은 요청에서 `spec.md`, `design.md`, `plan.md`, `tasks.md`가 한 번에 만들어져 수정 비용이 커진다.
- 실행 중에 새 정보가 발견되어도 이해 단계나 계획 단계로 되돌아가는 규칙이 약하다.
- 완료되지 않은 작업이나 검증 실패가 있어도 최종 응답이 성공처럼 보일 수 있다.

Claude Code는 이 문제를 Plan Mode와 TodoWrite를 분리해 다룬다. Plan Mode에서는 읽기와 계획 파일 수정만 허용하고, 사용자가 계획을 승인한 뒤에야 실제 구현을 시작한다. 실행 중 TODO는 계획을 대체하는 문서가 아니라 승인된 계획을 수행하기 위한 체크리스트로 사용한다.

## 목표

- Claude Code와 같은 방식으로 하로에 명시적인 Plan Mode를 도입한다.
- Plan Mode에서는 원칙적으로 실제 산출물, 코드, 설정, 사용자 파일을 수정하지 않는다.
- Plan Mode에서 수정 가능한 파일은 현재 계획/스펙 파일로 제한한다.
- 사용자가 승인하기 전에는 실행 단계로 넘어가지 않는다.
- 계획 산출물과 실행 TODO를 분리한다.
- 계획은 사용자 피드백으로 수정될 수 있고, 거절되면 Plan Mode에 남아 다시 수렴한다.
- 명확하고 저위험인 단일 작업은 과도한 Plan Mode 진입 없이 기존처럼 바로 처리할 수 있다.
- 새 스펙을 만들 때는 먼저 `spec.md`만 작성하고, 확정 전에는 `design.md`, `plan.md`, `tasks.md`를 만들지 않는다.

## 비목표

- v1에서 Claude Code의 모든 기능을 복제하지 않는다.
- v1에서 멀티 에이전트, 원격 계획 세션, 팀장 승인 mailbox를 도입하지 않는다.
- v1에서 모든 요청에 무조건 사용자 승인을 요구하지 않는다.
- v1에서 기존 tool-call fenced block 계약을 바꾸지 않는다.
- v1에서 파일 작업 권한, 저장 위치 정책, selected tools 차단 정책을 완화하지 않는다.
- v1에서 프론트엔드에 완전한 프로젝트 관리 UI를 새로 만들지 않는다.

## 핵심 개념

### Plan Mode

Plan Mode는 실행 전 탐색과 계획을 위한 제한 모드다.

허용되는 작업:

- 파일/코드/문서 읽기
- 검색과 구조 파악
- 사용자에게 요구사항 또는 의사결정 질문하기
- 지정된 계획 파일 또는 스펙 파일만 생성/수정하기

금지되는 작업:

- 실제 산출물 생성/수정/삭제
- 소스 코드 변경
- 설정 파일 변경
- 커밋, 푸쉬, 서버 재시작 같은 실행성 작업
- 계획 파일 외 파일을 수정하는 도구 호출

### Plan File

Plan File은 사용자 승인을 받기 위한 단일 계획 산출물이다.

스펙 작성 작업에서는 처음에 다음 파일만 Plan File 역할을 한다.

```text
.specs/draft/{spec}/spec.md
```

`spec.md` 확정 전에는 같은 스펙 폴더에 `design.md`, `plan.md`, `tasks.md`, `implementation.md`, `commits.md`를 만들지 않는다.

### Execution TODO

Execution TODO는 승인된 Plan File을 실행하기 위한 체크리스트다.

TODO는 다음 성격을 가진다.

- 계획을 대체하지 않는다.
- 요구사항을 새로 해석하는 문서가 아니다.
- 실행 순서와 현재 진행 상태를 보여준다.
- 동시에 하나의 TODO만 `in_progress`가 될 수 있다.
- 완료 기준을 충족하지 못하면 `done`으로 표시하지 않는다.

## 사용자 흐름

### 1. Plan Mode 진입 판단

다음에 해당하면 Plan Mode를 우선 제안하거나 자동 진입한다.

- 사용자가 "스펙", "계획", "설계", "어떻게 할지"를 요청한다.
- 데이터 모델, API, SSE, 도구 실행, 워크스페이스 정책이 바뀐다.
- 여러 파일이나 프론트엔드/백엔드를 함께 바꾸는 작업이다.
- 요구사항이 모호하거나 되돌리기 어려운 선택이 있다.
- 산출물 규모가 크거나 정량 기준이 있다.

다음은 Plan Mode 없이 바로 처리할 수 있다.

- 단일 파일의 작은 문구 수정
- 단순 질문 답변
- 명확한 단일 명령 실행
- 실패해도 쉽게 되돌릴 수 있는 저위험 작업

### 2. 이해와 탐색

Plan Mode에 들어가면 하로는 먼저 사용자 요청과 코드/문서 구조를 이해한다.

완료 조건:

- 작업 목적이 설명된다.
- 변경 대상 또는 산출물 대상이 식별된다.
- 사용자만 답할 수 있는 모호함이 분리된다.
- 기존 구현에서 재사용할 수 있는 패턴이 확인된다.

질문 조건:

- 사용자의 목표나 우선순위가 불명확하다.
- 여러 접근 방식의 UX/비용/위험 차이가 크다.
- 저장 위치, 변경 범위, 승인 기준이 애매하다.
- 정량 요구사항의 측정 단위가 없다.

### 3. 계획 파일 작성

하로는 탐색 결과를 `spec.md` 또는 지정된 Plan File에 점진적으로 기록한다.

Plan File에는 최소한 다음이 있어야 한다.

- 문제
- 목표
- 비목표
- 사용자 흐름 또는 동작 흐름
- 성공 기준
- 검증 기준
- 남은 질문 또는 결정 필요 사항

Plan File은 사용자가 빠르게 검토할 수 있어야 하며, 불필요한 배경 설명과 장황한 대안 나열을 피한다.

### 4. 계획 승인

Plan File이 충분히 수렴하면 하로는 사용자에게 승인을 요청한다.

승인 결과:

- 승인: Plan Mode를 종료하고 실행 단계로 이동한다.
- 거절 또는 피드백: Plan Mode에 남아 Plan File을 수정한다.
- 요구사항 변경: 필요하면 이해 단계로 되돌아간다.

### 5. 실행

실행 단계에서는 승인된 Plan File을 기준으로 Execution TODO를 만든다.

TODO 항목은 다음 정보를 가진다.

```json
{
  "id": "TODO-001",
  "title": "작업 제목",
  "status": "pending",
  "target": "대상 파일 또는 모듈",
  "action": "수행할 작업",
  "verification": "완료 확인 방법",
  "blocked_reason": null
}
```

상태 값:

- `pending`
- `in_progress`
- `done`
- `blocked`
- `failed`

규칙:

- 한 번에 하나의 TODO만 `in_progress`다.
- 작업을 시작하기 전에 해당 TODO를 `in_progress`로 바꾼다.
- 완료 즉시 `done`으로 바꾼다.
- 테스트 실패, 부분 구현, 도구 부족, 정책 차단, 사용자 의도 충돌이 있으면 `done`으로 표시하지 않는다.
- blocked가 발생하면 실행을 멈추고 계획 또는 이해 단계로 되돌아갈지 판단한다.

### 6. 최종 보고

최종 보고는 승인된 계획과 TODO 결과를 기준으로 생성한다.

보고 내용:

- 수행한 TODO
- 생성/수정된 파일
- 실행한 검증
- 충족한 성공 기준
- 남은 한계 또는 미완료 항목

미완료 TODO나 검증 실패가 있으면 성공처럼 말하지 않는다.

## 성공 기준

- 복잡한 작업은 실행 전 Plan Mode에서 문제/목표/비목표/성공 기준을 먼저 확정한다.
- 스펙 작성 요청은 `spec.md`만 먼저 만들고, 확정 전에는 나머지 문서를 만들지 않는다.
- Plan Mode에서는 계획 파일 외 파일 수정이 차단된다.
- 승인 전에는 실제 실행 도구가 호출되지 않는다.
- 사용자가 계획을 거절하면 피드백을 반영해 다시 Plan Mode에서 수렴한다.
- 승인 후 실행 단계에서는 TODO 상태가 순차적으로 갱신된다.
- blocked 발생 시 성공 보고를 하지 않고, 계획 또는 이해 단계로 되돌아갈 수 있다.
- 최종 보고는 실제 완료/검증 결과와 일치한다.

## 열린 질문

- Plan Mode 진입은 사용자가 명시적으로 요청한 경우만 자동으로 할지, 라우터가 고위험 작업으로 판단하면 자동 진입할지 결정이 필요하다.
- Plan File을 기존 `.specs` 문서로만 둘지, 일반 작업에도 별도 plan file을 둘지 결정이 필요하다.
- Plan Mode 상태를 DB에 영속화할지, 현재 intent turn/runtime state로만 관리할지 결정이 필요하다.
- 프론트엔드에 Plan Mode 배지와 승인 UI를 v1에 포함할지 결정이 필요하다.
